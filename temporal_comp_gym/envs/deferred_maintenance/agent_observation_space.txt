# Deferred Maintenance Task - Observation Space (protocol v2)

The agent receives a flattened 1D continuous array of observations at each time step. The environment is wrapped by `DeferredMaintenanceObservationWrapper` (in `wrappers.py`), which aggregates the raw dictionary data generated by `core.py` into the following structured vector (raw units, 25 values with `local_grid`):

## 1. Kinematics (6 values)
- `[0]` **pos_x**, `[1]` **pos_y**: position in the current stage (pixels; one cell = 50 px).
- `[2]` **vel_x**, `[3]` **vel_y**: velocity (pixels/s).
- `[4]` **angle**: rotation angle (radians).
- `[5]` **ang_vel**: angular velocity.

## 2. Micro-Navigation Sensors (8 or 9 values)
- **`local_grid` (9 values, v2 baseline)**: the cell type of the 3x3 neighbourhood of the rocket's cell:
  `0` = empty/danger void, `2` = path, `3` = code zone, `4` = station, `5` = exit, `6` = entry, `7` = stage boundary.
- **`raycasts` (8 values)**: normalised distance (0-1) to the first shape along 8 rays up to 150 px
  (the rocket itself is excluded).

## 3. Macro-Navigation Waypoint (2 values)
- Offset (dx, dy) in pixels from the rocket to the centre of the next path tile towards the exit
  (from the nearest path tile when the rocket is off the path).

## 4. Current Floor Code (1 value)
- `0.0`: not touching a station or code zone; otherwise the type id of the station/code zone touched.

## 5. Action Readiness Indicator (1 value)
- `0.0` before readiness, `1.0` from the moment the rocket enters the readiness stage.

## 6. Station Radar (2 values per code type)
- Offset (dx, dy) to the nearest station of each type, or `[-99, -99]` if none exists in the stage.

## Scaled observation used by the baselines
`MaintenanceScaledObservation` (applied by `agents/common/env_factory.py` for PPO, RecurrentPPO and PPO-RM)
rescales this to 28 values: positions and offsets in cells, velocities / 200, angular velocity / 10,
grid codes / 7, floor code / K, and the radar as (present, dx, dy) per type instead of the -99 sentinel.

## Episode structure (protocol v2)
- A seeded schedule is drawn at reset: readiness stage r in `readiness_delay_range` (inclusive, default 1-2),
  and one distinct code type per stage before r. Codes appear only in those stages.
- Every stage has one station per station type: the issued types, plus all other types when
  `distractor_stations=True` (v2 main condition). The station layout never depends on the held codes.
- A perfect run is therefore always possible: collect every code, service each one once ready, exit the last stage.
- `max_steps=4000` truncates the episode (the oracle's p95 length is ~1,860 steps).

## Info dictionary (protocol v2)
- `info["events"]`: `code_collected(k)`, `boundary_contact`, `service_attempt(k)` (hover timer reached),
  `off_path`, `stage_exit(s)`, `readiness_on`, `final_exit`, `stage_exit_incomplete`, in processing order.
- On the last step: `info["termination_cause"]` (`success`, `uncollected_codes_at_exit`,
  `held_codes_at_final_exit`, `timeout`) and `info["is_success"]`.
- `info["debug"]` (held/serviced/issued codes, readiness target, stage) only when `debug_info=True`.
